# Stage 4: Diagnose

1. In parallel:
   - `agents/face-validity.md`
   - `agents/completeness.md`
   - `agents/skeptical-reviewer.md`
   - `agents/developmental-advisor.md`
   - `agents/hypothesis-audit.md`, unless `stage-1/hypothesis_ledger.json` is missing (the ledger was skipped at Stage 1 or quarantined as `hypothesis_ledger.failed.json`) or its `mode` is `none`
   - the `diagnose` slot agents of each pack listed in `run.json` `packs`, primary pack first (none if the list is empty)
2. Each writes to `{WORKSPACE}/stage-4/`. Pass the user corrections from `brief.md` and the Stage 3 check-in answers to every agent.
3. Dispatch a compiler (judgment) that merges the stage-4 files into `stage-4/majors_draft.md`: the candidate major issues, ordered by consequence, each with severity, location, evidence, adjudication type, and why it matters for this contribution type. The user reads each issue at a check-in and decides whether to keep it, so give them enough to judge it without opening the paper. Carry the detail over from the source files rather than compressing it. Write in plain words, with no agent names or pipeline terms, and cite a page or table for every claim about the paper. Write each issue as:

   ```
   ## <n>. <One sentence naming the problem.>

   Severity: <label>. Adjudication: <paper | external | judgment>.
   Pack: <pack name | core>.

   What the paper claims: <One or two sentences on what the paper says or does at this point, with the page or table.>

   The problem: <Two to four sentences on what is wrong, with the specific evidence: the numbers, the table and column, the design feature, or the missing step.>

   Why it matters: <One or two sentences on what it does to the main claim, for this contribution type at this journal.>

   What would settle it: <The analysis, data, or change in the claim that would resolve it, and whether the paper already has part of it (give the page).>
   ```

   The heading sentence after `<n>.` is the issue's first sentence. Answers are matched to issues by that sentence, so keep it to one sentence and put nothing before it. Second-pack findings are capped at "Weakens a claim" unless they undermine the main claim. Findings from a pack in `run.json` `overlays` are capped the same way, except where that pack's severity rules set the level for a generated variable or nonlinear term whose role (in `fingerprint.md`, as corrected at the read check-in) is main treatment or main outcome (a generated variable) or main hypothesis (a nonlinear term). The same exception applies to any other overlay's fingerprint item whose role that pack's severity rules name as main, as corrected at the read check-in. The compiler reads `severity_rules` in `{PLUGIN}/packs/<pack>/pack.yaml` for each pack in `run.json` `packs` and applies each pack's rules to that pack's findings before the caps. Apply each rule once, to the level the pack's file gives; a rule that shifts a level (for example, down one level) is applied only by the compiler, and pack agents apply only rules that set a level. A shifting rule applies to the level the pack's own file gives, and the compiler's contribution-type reasoning must not discount the same finding again for the same reason. Where a pack file says it already discounted a finding for the contribution type, do not apply a shifting rule for the same reason. The compiler attributes each stage-4 file to a pack by slot ownership: a file written by the diagnose or theory agents of a pack in `run.json` `packs` (each agent's Output section names its file) holds that pack's findings, including issues a pack's theory agent wrote in Stage 3; a first line `Pack: <name>` is used when present. A second pack is a type pack in `run.json` `packs` other than `run.json` `primary_pack`; when `primary_pack` is null, every type pack is a second pack. When run.json has no primary_pack key, the pack for setup:type (the first entry of packs) is primary. A stage-4 file that starts `# Not run` holds no findings (a pack turned that check off by design). The compiler takes its pack notes as SKILL.md says (`stage-4-compiler`). When a pack's files carry `## Joint rule` sections, the compiler reads them across that pack's files and applies the pack's severity rules to each variable they name. When two source files raise the same problem about the same variable, term, table, or hypothesis, write one issue that carries the evidence from both and the severity that the owning pack's rules set, or, when no pack owns it, the better-evidenced of the two. A construct counts as a variable here, and if one of the two is the skeptic's core problem, the merged issue stays protected. The skeptic's issue in `stage-4/core_problem.md` is protected: it may be narrowed but never dropped. For each issue that rests on an alternative explanation in `stage-3/alternatives.md`, the compiler names that alternative's number. For each issue it also gives one sentence copied word for word from the paper where the problem shows, on a line starting `Excerpt:`, and the page the paper prints there, on a line starting `Page:`. The `Pack:` line names the pack whose agent wrote the issue's source file, by the slot attribution above, or `core` when a core agent (a file in `agents/`) wrote it. A merged issue takes the pack that owns it, or, when no pack owns it, the pack of the better-evidenced source.

4. Write `{WORKSPACE}/stage-4/questions.json` (schema in `shared/checkin-template.md`) with one card per major issue, item id `majors:<n>` (n = the issue's number in `majors_draft.md`), stop `majors`. A card for an issue that rests on alternative `<k>` carries `"depends_on": ["against:<k>"]` and `"prune_if": {"against:<k>": "C"}`, so an issue built on an alternative the user marked "Not plausible here" is never asked. Other cards have empty `depends_on` and `prune_if`. Never put the protected core-problem issue behind a `prune_if`. Ask the rounds that `plumb frontier {WORKSPACE}/stage-4/questions.json {WORKSPACE}` returns, up to four cards per screen. Where the `majors` stop is asked, first pin the cards to a working copy of the paper. Write `{WORKSPACE}/stage-4/majors_cards.json`: one record per card the first `frontier` call returns, with `id` (the issue's number n, as a string), `item` (`majors:<n>`), `title`, `severity`, `summary` (the issue's heading sentence and the first sentence of its "The problem:" line), `excerpt` and `ms_page` (from the issue's `Excerpt:` and `Page:` lines), and `pdf_page` null. RUN `python3 {PLUGIN}/skills/review/scripts/locate_issues.py <pdf> {WORKSPACE}/stage-4/majors_cards.json {WORKSPACE}/stage-4/majors_locations.json`, then `python3 {PLUGIN}/skills/review/scripts/annotate_pdf.py <pdf> {WORKSPACE}/stage-4/majors_cards.json {WORKSPACE}/stage-4/majors_locations.json {WORKSPACE}/checkin_majors_annotated.pdf`. Start the first screen with "Open {WORKSPACE}/checkin_majors_annotated.pdf to see each flag on its page." Where the stop is not asked, make no copy. An issue whose card was pruned is dropped from the majors; list it in `brief.md` under "Dropped with an alternative". Each card has the issue in two sentences, the page, and why it matters (paste into the chat first; see the check-in template). Options:
   - "A. Keep it as a major issue (Recommended)"
   - "B. It is real, but minor"
   - "C. The paper already addresses this (give the page)"
   - "D. Dig deeper before deciding"

   Show the context before asking (see the check-in template). Before each card's question, paste that issue in full: its heading sentence, severity, what the paper claims, the problem, why it matters, and what would settle it. Do not shorten or summarize it.

   For D, do not record a check-in. First log the request: `plumb log {WORKSPACE} dig_deeper '{"item":"majors:<n>","text":"<first sentence>"}'`. Then dispatch the pack or core agent that raised it with the instruction to look again, and ask again. A dig-deeper request is counted on its own, never as an override. For C, and before recording it, ASK a free-text follow-up: "Which page, and what does the paper say there?" Record the page for the Stage 6 advocate: create `{WORKSPACE}/stage-6/` if it does not exist yet, and append a line to `{WORKSPACE}/stage-6/advocate_pages.md` in the form `majors:<n>: p.<page> — <one-line claim>`, using the page and claim the user gave. Then record the C answer once, with the reply as its note: `plumb checkin {WORKSPACE} majors majors:<n> "<recommended label> | <first sentence>" "<chosen label> | <first sentence>" --note "p.<page>: <one-line claim>"`. In author mode, before accepting B or C on an issue rated "Undermines the main claim", show one line with the reason referees raise it and confirm.

   The major issues are numbered by an agent, so record and replay them by text as `shared/checkin-template.md` says ("Items numbered by an agent"). Record only the final answer for each issue, once (after any dig-deeper, re-ask, or page follow-up): `plumb checkin {WORKSPACE} majors majors:<n> "<recommended label> | <first sentence>" "<chosen label> | <first sentence>"`. At levels where the `majors` stop is not asked (see `stops_for` in `plumb/checkin.py`), take A for every card `frontier` returns, record it the same way with `--note auto` (a skipped stop's answer is never an override), and run `frontier` again until it is empty. Pruned issues are still dropped.
