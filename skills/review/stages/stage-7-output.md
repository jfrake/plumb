# Stage 7: Output

`{RUN}` is the run folder, the parent of `{WORKSPACE}`. The files the user chose go there, and everything else stays in `{WORKSPACE}`. `run.json` names the chosen `outputs` (`issues_list`, `annotated_pdf`, `report`, `editor_memo`) and the `issues_list_mode` (`"full"` or `"facts_only"`). The writers and the annotator take the issues to show only from `stage-7/validated.json`, and their places only from `stage-7/locations.json`.

At depth `quick`, Stage 7 runs every step below with these limits. The outputs can only be `issues_list` and `annotated_pdf`, and the issues list is always `"facts_only"`. Step 4 runs `plumb validate-output` and not the quote or citation scripts. There is no `qc.md`, so step 5 asks only the last question, step 6 reruns only `plumb validate-output`, and step 7 leaves out the quality-control counts. Pass the issues-list writer `stage-1/reference_list.md` (the reference-list check), `{WORKSPACE}/stage-2/summary_for_user.md`, and the recorded answer to the read check. If `summary_for_user.md` does not exist (the ledger gate failed at Quick, so Stage 2 skipped the summary and the read check), do not pass it; tell the writer instead to state in one plain sentence under "## Did we read it right?" that the tool could not build a reliable reading of how the variables are constructed, so the check was skipped.

At every depth, if `types_without_pack` in `run.json` is not empty, tell the issues-list writer and the editor-memo writer, whichever run, to state in one plain sentence that no pack is built for that paper type, so the methods diagnosis is limited. If `core_adjust` `off` in `run.json` is not empty, also tell those two writers to state in one plain sentence which checks were skipped by design for this paper and why, naming each in plain words (for example "setting research" or "the variable ledger"), never by file name and never as a failure. The editor memo puts this sentence, and the no-pack sentence, as the last sentence of `## The paper`. Never pass either sentence to the report writer: the mock report reads as a human referee's report and says nothing about how the review was produced.

1. Validated issues. Run `plumb validated {WORKSPACE}`. It keeps an issue only when it survived the audit (it is still in `stage-6/issues.json`), the user kept it at the `numbers`, `majors`, and `minors` check-ins (an answer the tool took counts as kept), and its facts are confirmed (none of its cells is in `stage-1/unverified_numbers.md`, and its reference lookup did not fail). It writes `{WORKSPACE}/stage-7/validated.json`, the kept issues most serious first, each with its `id`, and `{WORKSPACE}/stage-7/dropped.json`, each dropped item with its reason. It prints the two counts.
   - Exit 1 lists issues that have no excerpt from the paper. Re-dispatch `agents/adjudicator.md` with the list and "Add to each listed issue in `{WORKSPACE}/stage-6/issues.json` an `excerpt`: one sentence copied word for word from the paper where the issue shows." Run `plumb validated {WORKSPACE}` again, up to `revisions` times. If issues still have none, run `plumb validated {WORKSPACE} --allow-missing-excerpt`, which places them by page alone, and log `plumb log {WORKSPACE} dependency '{"name":"excerpt","message":"some issues have no excerpt from the paper; they are placed by page"}'`.
   - Exit 3 lists issues whose summary is not in `stage-6/draft.md` word for word, so the accuracy audit never checked it. Re-dispatch `agents/adjudicator.md` with the list and "Re-derive every issue's record from the audited draft." Run `plumb validated {WORKSPACE}` again, up to `revisions` times. If it still exits 3, show the message and stop.
   - Exit 2 means an input is missing, is not valid JSON, or has the wrong shape. Show the message, which names the file, and stop. Treat it as a stop, never as issues with no excerpt.
2. Locations. RUN `python3 {PLUGIN}/skills/review/scripts/locate_issues.py <pdf> {WORKSPACE}/stage-7/validated.json {WORKSPACE}/stage-7/locations.json`. For each issue it writes the PDF page, the spot on the page, how it was found (`exact`, `page_only`, `approximate`, or `not_found`), and a `label` such as "ms p. 30 (PDF p. 32)". Log the counts it prints: `plumb log {WORKSPACE} verification '{"check":"locate_issues","methods":<the printed counts>}'`.
3. Write each chosen output. Numbers left unverified at the `numbers` check-in are entries in `dropped.json`, so they appear only in the issues list's dropped-items appendix; no writer lists them anywhere else.
   - `issues_list`: dispatch `agents/issues-list-writer.md` with `MODE=<issues_list_mode>`. It writes `{RUN}/issues_list.md`.
   - `report`: dispatch `agents/report-writer.md`. It writes `{RUN}/mock_report.txt` from the issues in `validated.json` alone, and `{WORKSPACE}/stage-7/report_trace.json`, which maps each comment's number to the ids of the issues it raises. When `permission` in `run.json` is `journal` (a journal sent the paper for review), add as the last line of the report, after the last reference: "I used Plumb, an AI review tool, to check this report. The judgments and conclusions are my own."
   - `annotated_pdf`: RUN `python3 {PLUGIN}/skills/review/scripts/annotate_pdf.py <pdf> {WORKSPACE}/stage-7/validated.json {WORKSPACE}/stage-7/locations.json {RUN}/<paper-stem>_annotated.pdf`, with `<paper-stem>` the PDF's file name without `.pdf`. It writes a copy and never changes the original. Log the counts it prints: `plumb log {WORKSPACE} verification '{"check":"annotate_pdf","placed":<the printed counts>}'`.
   - `editor_memo`: dispatch `agents/editor-memo-writer.md` with `MODE=<issues_list_mode>`. Pass it only `{WORKSPACE}/stage-7/validated.json`, `{WORKSPACE}/stage-7/locations.json`, and `{WORKSPACE}/paper_summary.md`. This DISPATCH is an exception to SKILL.md's rules: do not pass `PDF_PATH`, `PAGE_COUNT`, or `shared/contracts.md`. It writes `{RUN}/editor_memo.md`: a neutral summary of the paper and the five most serious validated issues, or all of them when fewer survived, with no recommendation.
4. Check each prose output. On exit 1 from any check, send the messages back to its writer and check again, up to `revisions` times; if they persist, show them at the check-in in step 5. A citation failure for a reference that already has a `citation_check` dependency event in `{WORKSPACE}/audit/events.jsonl` (the user kept it as not verified in Stage 6, or the run took that answer on its own) is not sent back, because a writer cannot fix it; it goes straight to the "Not verified:" block in step 6. Log each result: `plumb log {WORKSPACE} verification '{"check":"<check>","output":"<output>","exit":<code>}'`.
   - `issues_list`: `plumb validate-output issues_list {RUN}/issues_list.md --mode <issues_list_mode> --validated {WORKSPACE}/stage-7/validated.json --dropped {WORKSPACE}/stage-7/dropped.json --run {WORKSPACE}/run.json`.
   - `report`: `plumb validate-output report {RUN}/mock_report.txt --permission <permission> --validated {WORKSPACE}/stage-7/validated.json --trace {WORKSPACE}/stage-7/report_trace.json --run {WORKSPACE}/run.json`, with `<permission>` from `run.json`. With `journal` it fails unless the disclosure line is the last line. A comment that does not trace to an issue in `validated.json` fails, and so does an issue no comment raises.
   - `editor_memo`: `plumb validate-output editor_memo {RUN}/editor_memo.md --validated {WORKSPACE}/stage-7/validated.json --mode <issues_list_mode> --run {WORKSPACE}/run.json`. It checks the format, both page numbers, that the items are the first five issues in `validated.json` in order (with the one sentence when fewer survived), that `MODE facts_only` drops "Why it matters" and "What would settle it", and that the memo carries no verdict, score, or desk-reject signal.
   - For each prose output, with `<file>` its path and `<output>` its name (`issues_list`, `report`, or `editor_memo`): `python3 {PLUGIN}/skills/review/scripts/verify_quotes.py <file> <pdf> {WORKSPACE}/stage-7/<output>_quotes {WORKSPACE}/extracted_tables`, and `python3 {PLUGIN}/skills/review/scripts/verify_citations.py <file> {WORKSPACE}/stage-7/<output>_citations.md <config contact_email> --workspace {WORKSPACE}`. For the citation check, exit 2 means network trouble: log `plumb log {WORKSPACE} dependency '{"name":"citation_lookup","message":"network trouble; see stage-7"}'` and continue.

<!-- CHECKIN: draft -->
5. Draft review, asked once about all the chosen outputs together. First give the path of each chosen output. Then one question per major-issue ruling in `qc.md`, showing the proposed ruling and its evidence (paste into the chat first; see the check-in template). Say each ruling in plain words: what the audit proposes to change and the page that shows why, never its tag or its section name in `qc.md`. Options: "A. Accept the ruling (Recommended)" and "B. Overturn it". Then one question: "A. The outputs are ready (Recommended)", "B. Ask for edits", "C. Show me the quality-control record".
   - Item ids: `draft:ruling:<n>` for each ruling (n = the issue's number in the draft), and `draft:ready` for the last question. Record each answer with `plumb checkin {WORKSPACE} draft <item> "<recommended label>" "<chosen label>"`.
   - For B on a ruling, dispatch `agents/adjudicator.md` once with the overturned rulings and the instruction to reverse them by editing `{WORKSPACE}/stage-6/draft.md`, `{WORKSPACE}/stage-6/issues.json`, and `qc.md` in place. It must never rebuild from the Stage 5 draft, so the Stage 6 accuracy fixes survive. Then redo steps 1 to 4. A protected finding still holds: the core problem stays in, and a fabricated citation stays out.
   - For B on the last question, ASK for the edits as free text. To remove an item, record `plumb checkin {WORKSPACE} draft draft:drop:<source> "Keep (Recommended)" "Drop: <its title>"`, with `<source>` the item's `source` in `validated.json`; `plumb validated` then lists it under dropped items as "you dismissed it". An edit that changes an issue's wording, severity, or page goes into `{WORKSPACE}/stage-6/issues.json` and `{WORKSPACE}/stage-6/draft.md` first. After either, redo steps 1 to 4, so every output shows the same issues. Apply any other edit to the output it names and re-run step 4. Then ask the last question again. For C, show `qc.md` (paste into the chat first; see the check-in template) and ask again. Record only the final answer.
   - At levels where the `draft` stop is not asked (see `stops_for` in `plumb/checkin.py`), take A for every question and record it the same way with `--note auto` (a skipped stop's answer is never an override).
6. Final verification, after the draft review's last answer and after any edit loop it started. Check each chosen output exactly as it sits in `{RUN}`, and rebuild nothing after this step: no writer, `plumb validated`, `locate_issues.py`, or `annotate_pdf.py` runs again.
   - `issues_list`: `plumb validate-output issues_list {RUN}/issues_list.md --mode <issues_list_mode> --validated {WORKSPACE}/stage-7/validated.json --dropped {WORKSPACE}/stage-7/dropped.json --run {WORKSPACE}/run.json` (the both-page-numbers rule is part of it).
   - `report`: `plumb validate-output report {RUN}/mock_report.txt --permission <permission> --validated {WORKSPACE}/stage-7/validated.json --trace {WORKSPACE}/stage-7/report_trace.json --run {WORKSPACE}/run.json` (report traceability and the disclosure line are part of it).
   - `editor_memo`: `plumb validate-output editor_memo {RUN}/editor_memo.md --validated {WORKSPACE}/stage-7/validated.json --mode <issues_list_mode> --run {WORKSPACE}/run.json` (both page numbers and the no-verdict rule are part of it).
   - For each prose output (`issues_list`, `report`, `editor_memo`), except at Quick depth: `python3 {PLUGIN}/skills/review/scripts/verify_quotes.py <file> <pdf> {WORKSPACE}/stage-7/last_check/<output>_quotes {WORKSPACE}/extracted_tables` and `python3 {PLUGIN}/skills/review/scripts/verify_citations.py <file> {WORKSPACE}/stage-7/last_check/<output>_citations.md <config contact_email> --workspace {WORKSPACE}`. A citation check that exits 2 (network trouble) is logged as a dependency, as in step 4, and does not count as a failure. Its final event below uses `"step":"verify_citations"` with `"exit":2`, and the README reads it as verified, with a note that citation lookup was unavailable.
   - `annotated_pdf`: it was built in step 3 from the final `validated.json` and `locations.json`. RUN `python3 {PLUGIN}/skills/review/scripts/annotate_pdf.py --check {RUN}/<paper-stem>_annotated.pdf`. It exits 0 when the file exists, opens as a PDF, and starts with the index page, and 1 otherwise, with the reason. If it fails, tell the user the reason; the README will mark the file "Not verified."
   - If a check on a prose output fails (possible only when failures persisted to the draft review and the user answered "ready", or when a reference was kept as not verified in Stage 6), first deal with any failure that names an editorial recommendation, a verdict, or a desk-reject signal. Such a sentence never ships. Remove the sentence the failure names from the file and rerun that output's `plumb validate-output`. Repeat while a failure still names one, with at most three removals in all. If one still remains, move the file to `{WORKSPACE}/stage-7/withheld/` with `plumb put {RUN} .workspace/stage-7/withheld/<name> --from {RUN}/<name>`, tell the user in one plain line that I withheld it because it still carried a recommendation, and skip its other checks; `plumb readme` marks it "Withheld." Then, for any other failure that remains, write a block at the very top of the file, before anything else: a line "Not verified:" and then one line per failure, "<check>: <message>", with no bullet marks and no words copied from the failing text. Never deliver a failing output without that block.
   - Then, for each chosen output, get its hash with `plumb sha256 <file>` and log one event per check: `plumb log {WORKSPACE} verification '{"check":"final","output":"<output>","file":"<file name>","sha256":"<sha256>","step":"<check>","exit":<code>}'`. For the annotated PDF, log one event with `"step":"check"` and the exit code of its check. The audit package then shows that the delivered files are the files that were checked, and `plumb readme` marks each output "Verified." or "Not verified." from these events. It counts only the events logged after the last `draft:ready` answer whose `sha256` matches the file as it is now.
7. Finish the run folder. Run `plumb usage report {WORKSPACE}`. It reads the transcripts the usage hook pointed to and writes `{WORKSPACE}/usage.json`: input, output, cache-write, and cache-read tokens, time, and API-equivalent cost, by stage and by model, with the stress test's Codex tokens when Codex reported them. Where the platform runs no plugin hooks it records "Usage not measured in this app." It also writes `{WORKSPACE}/models.json`, the model record: the exact model ids observed in the transcripts, the work each did (mechanical or judgment), and the call counts; where usage was not measured it lists the configured tier aliases and says they are aliases, not observed ids. It is advisory: on a non-zero exit, log `plumb log {WORKSPACE} dependency '{"name":"usage_report","message":"the usage report failed; the README has no usage totals"}'` and continue. Then run `plumb render-audit {WORKSPACE}`, which writes `audit_package.md`. Then run `plumb readme {WORKSPACE} --profiles {PLUGIN}/profiles`. It writes `{RUN}/README.md`, which says what each file is and whether it was verified, gives the paper, depth, level, journal, whose permission covers the paper, and date, reports the run's usage, and names the record files in `.workspace/`, the audit package among them. Then copy `{WORKSPACE}/paper_summary.md` to `{RUN}/paper_summary.md`. Log `plumb log {WORKSPACE} output '{"final":true,"files":["<each file written to the run folder>"]}'`, which marks the run finished and writes the Stage 7 line in the run log, so resume does not offer it again and the usage hook stops recording for it. Tell the user the run folder's path and that `README.md` there explains each file. Run `plumb counts {WORKSPACE}`. In plain words, say: how many issues the audit kept, dropped, or reworded (read the Upheld, Overruled, and Reframed counts from `qc.md`; do not say these section names); how many times the user chose differently from my recommendation, out of how many answers (read `override` and `user_answers` from `plumb counts`; do not say these names); how many calls the user left to me (read `delegations` from `plumb counts`; do not say this name); how many answers I took because the level skips that stop (read `auto_answers` from `plumb counts`; do not say this name); and, as a separate number, how many times the user asked me to look deeper (read `dig_deeper` from `plumb counts`; do not say this name). Then append this stage's `Scoreboard 7:` line to `brief.md` (see SKILL.md), run `plumb scoreboard {WORKSPACE}`, and paste the table it prints. This is the one time the run shows the scoreboard.
8. Ask: "Anything you plan to edit or felt was off? I can note it for future runs." Save any answer to `{WORKSPACE}/feedback.md`. A later version will learn from this file.
